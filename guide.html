คู่มือ Phat Skills สำหรับ AI Coding Agents

Phat Skills คืออะไร?

Phat Skills คือชุด 23 Agent Skills แบบโอเพนซอร์สสำหรับ Codex และ coding agents ที่รองรับ Agent Skills format ช่วยเชื่อมการตัดสินใจเรื่องโปรดักต์ การเก็บ context การเขียน spec การพัฒนา การทดสอบ และ code review

เริ่มด้วย $ask-workflow เพื่อเลือกขั้นตอนถัดไปจากสถานะโปรเจกต์จริง แต่ละ skill เก็บคำแนะนำในไฟล์ SKILL.md และเผยแพร่ภายใต้ MIT License

ผู้จัดทำ: PhatYSD · Source repository · ข้อกำหนดการทำงานให้ยึด workflow contract และ SKILL.md ต้นฉบับ

วิธีติดตั้ง Phat Skills

ติดตั้งจาก canonical GitHub repository ผ่าน skills CLI โดยตัวอย่างนี้ใช้ Codex เป็น agent เป้าหมาย

Before you start

ต้องมี Node.js และ npm ที่เรียก npx ได้ พร้อม internet สำหรับดาวน์โหลด package และ repository เปิด terminal ในโปรเจกต์ที่ต้องการใช้งาน

01 / Discover the pack

ดูรายการ skills ก่อนติดตั้ง คำสั่งนี้แสดง catalog โดยไม่ติดตั้ง skills

TERMINAL
npx skills@latest add https://github.com/phatysddev/skills --list

02 / Choose your installation

Start with one skill

ติดตั้ง router เพื่อแนะนำขั้นตอนถัดไป เมื่อใช้ subset ให้ติดตั้ง workflow และ utility ที่งานนั้นต้องใช้เพิ่มด้วย

TERMINAL
npx skills@latest add https://github.com/phatysddev/skills --skill ask-workflow --agent codex --yes

Install the complete pack

ติดตั้งทั้ง 23 skills สำหรับโปรเจกต์ปัจจุบัน ครอบคลุม workflow, utilities, prototype และ verification

TERMINAL
npx skills@latest add https://github.com/phatysddev/skills --skill '*' --agent codex --yes

Use it across projects

เพิ่ม --global เมื่อต้องการติดตั้งระดับผู้ใช้แทนโปรเจกต์ปัจจุบัน

TERMINAL
npx skills@latest add https://github.com/phatysddev/skills --skill ask-workflow --agent codex --global --yes

Include security support

เมื่อติดตั้งบางสกิล ให้เพิ่ม agent-security เพื่อใช้ร่วมกับงาน research และ workspace ของสกิลหลัก

TERMINAL
npx skills@latest add https://github.com/phatysddev/skills --skill agent-security --agent codex --yes

ดูวิธีใช้ agent-security ร่วมกับ workflow →

03 / Start a conversation

เปิด coding agent ในโปรเจกต์ที่ติดตั้ง แล้วเริ่มด้วย prompt นี้ ตัวอย่างใช้รูปแบบเรียก skill ของ Codex

AGENT PROMPT
$ask-workflow
อ่านสถานะโปรเจกต์นี้ แล้วแนะนำขั้นตอนถัดไปพร้อมเหตุผล

ถ้า agent ไม่เห็น skill ให้ตรวจ agent เป้าหมายและ scope การติดตั้ง จากนั้นเปิด session ใหม่ หากใช้ agent อื่น ให้ใช้รูปแบบ invocation ที่ agent นั้นรองรับ

Installation notes

--yes ข้ามคำถามยืนยันของ installer ส่วนคำสั่งไม่มี flags จะให้เลือก skill และ agent ระหว่างติดตั้ง การติดตั้ง skill ไม่ได้ติดตั้ง test runner หรือ dependency ของโปรเจกต์ให้เอง

อ้างอิง: skills CLI documentation ↗ และ Phat Skills README ↗

เลือกเวิร์กโฟลว์ให้ตรงกับโปรเจกต์

เลือกเส้นทางตามสถานะของโปรเจกต์ ไม่จำเป็นต้องเรียกทุก skill ทุกครั้ง

A new project

DEFAULT PATH
ask-workflow → grill-workflow
  → grill-design (optional)
  → setup-project → write-spec → to-tasks
  → implement-task → selected verification → code-review

grill-workflow ช่วยคลี่คลายการตัดสินใจ ส่วน setup-project บันทึกบริบทถาวร เมื่อ spec พร้อมแล้วจึงแยก tasks และเริ่ม implementation

An existing codebase

BROWNFIELD PATH
ask-workflow → code-to-context
  → setup-project → write-spec → to-tasks

เมื่อ onboarding ต้องการข้อมูล repository เพิ่มและการอ่านเฉพาะจุดไม่เพียงพอ ให้ code-to-context อ่าน repo ก่อน โดยแก้เฉพาะ generated Codebase Context และรักษาบริบทที่มนุษย์เขียนไว้

When seeing the UI helps

OPTIONAL PROTOTYPE PATH
setup-project → to-prototype
  → edit-prototype (repeat as needed)
  → spec-with-prototype → to-tasks

ใช้ prototype เพื่อตรวจ navigation, hierarchy, states หรือ interaction แล้วนำสิ่งที่ยอมรับกลับเข้า spec ก่อนแยก tasks โดย grill-design เป็นตัวเลือกสำหรับกำหนดทิศทาง UI และ ui-design เป็น utility ที่ช่วยภายในงาน

From ready to reviewed

TASK LIFECYCLE
todo → in_progress → in_review → done
                    ↘ blocked (record the unblock condition)

implement-task ทำทีละงาน ตรวจสอบตาม policy แล้วส่งเข้า in_review ส่วน code-review เป็นผู้ตัดสินว่า ready for done หรือส่ง findings กลับไปแก้

Working through a batch

เรียก $auto-implement เมื่อมี tasks อยู่แล้วและอนุญาตขอบเขตชัดเจน ระบบตรวจ user-action blockers ทั้งชุดก่อนเริ่ม จากนั้นทำทีละ task ตาม dependency โดยยังรักษา verification และ review เดิม การอนุญาต batch ไม่ได้อนุญาต commit, push หรือ deploy โดยอัตโนมัติ

Security support across the workflow

agent-security เป็นสกิลย่อยที่สกิลหลักโหลดก่อน research docs หรือทำงานกับไฟล์และคำสั่ง โดยรักษาขอบเขตและการตรวจสอบเดิม

ดูวิธีใช้ agent-security ร่วมกับ workflow →

การทดสอบและรีวิว

กำหนดระดับการตรวจให้เข้ากับโปรเจกต์ โดยแยก unit tests, integration tests, E2E และ code review ออกจากกัน

Three modes, per capability

setup-project ถามนโยบายหนึ่งครั้งและบันทึกเป็นค่าเริ่มต้นให้ implement-task โดยสามารถระบุ override สำหรับ task ได้

ModeBehavior
autoทำเมื่อเกี่ยวข้องและมี installed skill กับ runner ที่รองรับ มิฉะนั้นบันทึกเหตุผลที่ข้าม
requiredเมื่อเกี่ยวข้อง ต้องมี capability พร้อมใช้งานและผ่านการตรวจ ไม่เช่นนั้น block
offไม่เรียก capability นั้นและบันทึกว่า policy กำหนดให้ข้าม

One final review

VERIFICATION SEQUENCE
implement-task
  → selected test sub-agents
  → integrate fixes + final checks
  → in_review
  → one final code-review
  → done (only after approval)

แต่ละ test capability ที่เลือกทำงานผ่าน sub-agent ของตัวเองตามลำดับ ตัวหลักรวมผลและแก้ implementation ก่อนส่ง final reviewer เพียงหนึ่งครั้งหลังเข้า in_review

Clear ownership

  • Test sub-agents แก้เฉพาะ test files ที่อยู่ในขอบเขต task
  • Main agent เป็นเจ้าของ implementation fixes และ final verification
  • Final reviewer แก้ได้เฉพาะ review evidence และสถานะ task ที่เลือก
  • ไม่ติดตั้ง capability ที่หายไปเอง หาก delegation ใช้ไม่ได้ ให้จัดการตาม auto/required policy
  • Review เป็นขั้นตอนสุดท้ายเสมอเมื่อ policy อนุญาตให้เรียก และไม่ถูกแทนด้วยผล tests

Select tests by relevance

Unit tests ตรวจ logic แยกส่วน Integration tests ตรวจ boundary ระหว่างส่วนของระบบ E2E ตรวจเส้นทางใช้งานสำคัญ ไม่ต้องเรียกทุกตัวกับทุกงาน การข้ามต้องมีเหตุผล ส่วน code review ที่ไม่ใช่ off ใช้กับทุก implementation task

ใช้ agent-security ร่วมกับ workflow

ใช้สกิลหลักตามปกติ เช่น implement-task หรือ auto-implement โดย agent-security ช่วยตรวจข้อมูลภายนอกและผลกระทบก่อนทำงานบนเครื่อง

One supporting skill, throughout the workflow

สกิลเดิมทั้ง 22 ตัวเชื่อมกับ agent-security ภายในงาน ไม่ต้องเรียกเป็นขั้นตอนใหม่หรือเพิ่มโหมด verification

Parent skillsSecurity support
ask-workflow, grill-workflow, grill-design, setup-project, write-spec, to-tasks, change-scope, spec-with-prototypeแยกข้อมูลจากแหล่งภายนอกออกจากข้อตกลงและคำอนุมัติของผู้ใช้
code-to-context, compact-contextรักษาที่มาของข้อมูลใน context และ handoff โดยไม่เปลี่ยนคำกล่าวอ้างให้เป็นคำอนุมัติ
implement-task, auto-implement, debug-task, to-prototype, edit-prototype, ui-designตรวจคำสั่ง ไฟล์ที่เข้าถึง และผลข้างเคียงก่อนทำงานภายในขอบเขตที่อนุญาต
unit-test, integration-test, e2e-test, code-review, verify-feature, release-checkตรวจ runners และ hooks พร้อมรักษาขอบเขตของ agent ที่รับงานต่อและรายงานสิ่งที่ตรวจไม่ได้

Docs provide evidence, not permission

หาก docs แทรกคำสั่งให้ส่ง secrets เปลี่ยนการตั้งค่า agent หรือรันคำสั่งนอกงาน ให้ข้ามข้อความนั้นและใช้ข้อมูลเทคนิคที่ตรวจสอบได้ต่อ

ตรวจผลข้างเคียงของ scripts และ hooks ก่อนรัน งานปกติที่เข้าใจและได้รับอนุญาตแล้วดำเนินต่อได้ หากการตรวจที่จำเป็นทำไม่ได้อย่างปลอดภัย ให้รายงานช่องว่างนั้นแทนการอ้างว่าผ่าน

agent-security เป็นคำแนะนำสำหรับ agent และใช้ร่วมกับ sandbox และ permissions ของ host

Install alongside your workflow

การติดตั้งทั้งแพ็กมี agent-security รวมอยู่แล้ว หากเลือกติดตั้งบางสกิล ให้เพิ่ม agent-security ร่วมกับสกิลหลักและ capabilities ที่งานนั้นต้องใช้

Frequently asked questions

ต้องติดตั้งทั้ง 23 skills ไหม?

ไม่จำเป็น เลือกติดตั้งด้วย --skill ได้ แต่ workflow บางตัวใช้ utility ร่วมกัน เช่น ui-design ในงาน UI ควรติดตั้ง skill ที่เกี่ยวข้องกับเส้นทางที่จะใช้ให้ครบ

ใช้กับโปรเจกต์ที่มีโค้ดอยู่แล้วได้ไหม?

ได้ เริ่มด้วย ask-workflow เพื่อทำ task เดิมต่อ ใช้ code-to-context เฉพาะ onboarding หรือช่องว่างบริบทสำคัญ ไม่ refresh เพียงเพราะ commit เปลี่ยน

ต้องทำ prototype ทุกครั้งไหม?

ไม่ต้อง Prototype เป็นทางเลือกเมื่อการเห็น UI ช่วยลดความไม่แน่ใจเรื่อง flow, states หรือโครงหน้า ถ้าพฤติกรรมชัดแล้วไป write-spec ได้เลย

auto-implement จะ push หรือ deploy ให้ไหม?

การอนุญาตให้ทำ task batch ไม่ได้อนุญาต commit, push หรือ deploy งานเหล่านี้ต้องเป็นไปตามคำสั่งผู้ใช้และ policy ที่เกี่ยวข้อง

ถ้าไม่มี test runner จะเกิดอะไรขึ้น?

โหมด auto บันทึกเหตุผลที่ข้ามเมื่อ capability ไม่พร้อม โหมด required จะ block เมื่อการตรวจนั้นเกี่ยวข้องแต่ทำไม่ได้ และไม่ติดตั้ง missing capability ให้เอง

ใช้ในงานเชิงพาณิชย์ได้ไหม?

ได้ โปรเจกต์เผยแพร่ภายใต้ MIT License ให้รักษา copyright และ license notice ตามเงื่อนไข รายละเอียดอ่านได้ที่ LICENSE ใน source repository

Skill รุ่นเก่าชื่อไม่ตรงกับเอกสารนี้?

สกิลบางตัวเปลี่ยนชื่อแล้ว เช่น ask-phat → ask-workflow และ review-with-phat / review-task → code-review ต้องใช้ชื่อปัจจุบันในการเรียกและติดตั้ง ชื่อเก่าไม่ใช่ aliases ดูชื่อเทียบทั้งหมดใน docs/migrations/skill-identifier-migration.md ของ repository

รายการ Agent Skills ทั้ง 23 ตัว

ask-workflow

ให้ agent อ่านสถานะโปรเจกต์และแนะนำขั้นตอนถัดไปเพียงขั้นตอนเดียว

ใช้เมื่อ: ยังไม่แน่ใจว่าควรเริ่มตรงไหน

ตัวอย่างและวิธีใช้ ask-workflow · อ่าน SKILL.md ต้นฉบับ

grill-workflow

ถามให้ชัดเรื่องปัญหา ขอบเขต กฎธุรกิจ และข้อจำกัด ก่อนเขียน spec

ใช้เมื่อ: มีไอเดีย แต่ยังมีการตัดสินใจที่ค้างอยู่

ตัวอย่างและวิธีใช้ grill-workflow · อ่าน SKILL.md ต้นฉบับ

grill-design

บันทึกทิศทาง UI ที่ตกลงร่วมกัน เพื่อให้ขั้นตอนออกแบบใช้ข้อมูลชุดเดียวกัน

ใช้เมื่อ: ต้องการกำหนด visual direction แบบเฉพาะ

ตัวอย่างและวิธีใช้ grill-design · อ่าน SKILL.md ต้นฉบับ

setup-project

จัดทำบริบทโปรเจกต์ เอกสารนำทาง และนโยบายการตรวจสอบงาน

ใช้เมื่อ: ตัดสินใจเรื่องโปรดักต์แล้ว แต่ยังไม่มีบริบทถาวร

ตัวอย่างและวิธีใช้ setup-project · อ่าน SKILL.md ต้นฉบับ

write-spec

เขียน behavioral specification ที่มีขอบเขตและ acceptance criteria ชัดเจน

ใช้เมื่อ: requirements พร้อมสำหรับการระบุพฤติกรรม

ตัวอย่างและวิธีใช้ write-spec · อ่าน SKILL.md ต้นฉบับ

to-tasks

แยก spec ที่พร้อมแล้วเป็นงานย่อยที่ตรวจสอบได้ พร้อมลำดับ dependency

ใช้เมื่อ: มี spec ที่พร้อมนำไปพัฒนา

ตัวอย่างและวิธีใช้ to-tasks · อ่าน SKILL.md ต้นฉบับ

implement-task

ทำงานหนึ่ง task ให้ครบขอบเขต พร้อมหลักฐานตรวจสอบตามนโยบายโปรเจกต์

ใช้เมื่อ: มี task ที่พร้อมพัฒนา

ตัวอย่างและวิธีใช้ implement-task · อ่าน SKILL.md ต้นฉบับ

auto-implement

ตรวจ blockers ทั้งชุดก่อน แล้วทำ task ตาม dependency ทีละงาน

ใช้เมื่อ: มี task หลายรายการและต้องการอนุญาตให้ทำเป็นชุด

ตัวอย่างและวิธีใช้ auto-implement · อ่าน SKILL.md ต้นฉบับ

code-review

ตรวจ implementation เทียบกับ spec และ acceptance criteria ก่อนตัดสินว่า done

ใช้เมื่อ: implementation พร้อมรับการ review

ตัวอย่างและวิธีใช้ code-review · อ่าน SKILL.md ต้นฉบับ

change-scope

ปรับ requirement, spec และ task ตามขอบเขตใหม่ โดยรักษางานและหลักฐานเดิมที่ยังใช้ได้

ใช้เมื่อ: เปลี่ยนพฤติกรรมที่ตกลงไว้หลังวางแผนหรือเริ่มพัฒนา

ตัวอย่างและวิธีใช้ change-scope · อ่าน SKILL.md ต้นฉบับ

code-to-context

ใช้เมื่อ: ต้อง onboarding หรือเติมช่องว่างข้อมูล repository ที่สำคัญ

ตัวอย่างและวิธีใช้ code-to-context · อ่าน SKILL.md ต้นฉบับ

ใช้เมื่อ: handoff ยาวหรือซ้ำซ้อน

ตัวอย่างและวิธีใช้ compact-context · อ่าน SKILL.md ต้นฉบับ

ใช้เมื่อ: พบ bug หรือ regression ที่ยังไม่ทราบสาเหตุ

ใช้เมื่อ: agent research docs หรือทำงานกับไฟล์ คำสั่ง และเครื่องภายในขอบเขตงาน

ตัวอย่างและวิธีใช้ agent-security · อ่าน SKILL.md ต้นฉบับ
